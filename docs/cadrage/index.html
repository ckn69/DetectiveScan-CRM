Synthèse & décisions

Ce dossier répond aux 14 points de ta demande, dans l'ordre. Aucune ligne de code applicative n'est écrite. Chaque décision structurante est expliquée avec son alternative : réponds « validé » ou indique ce que tu changes, avec tes réponses aux questions de la section 14.

Direction artistique provisoire. Je n'ai pas pu lire detectivescan.com : le domaine est bloqué par la politique réseau de mon environnement de travail. Les couleurs et typographies de ce dossier sont une proposition construite sur ton brief (premium, hôtelier, mystérieux, élégant). Elles sont toutes centralisées en variables : envoie ton logo et tes codes couleurs, ou autorise le domaine, et je réaligne l'ensemble en une passe.

L'essentiel en cinq points

  1. Trois surfaces, un seul produit. L'expérience joueur (go.), l'espace hôtelier (app.) et le back-office (admin.) sont trois applications web distinctes. Elles partagent une base Postgres hébergée en Europe, cloisonnée hôtel par hôtel.
  2. Le MVP prouve la valeur pour l'hôtel. Association QR ↔ chambre, suivi des scans et des parties, avis, campagnes de 3 secondes, et un back-office pour créer les hôtels, les QR codes et les abonnements.
  3. CRM, agenda, signature et coffre-fort passent en V2. Ils se branchent par adaptateurs, ce qui permet d'intégrer ton code open source sans l'emmêler au cœur du produit.
  4. Les joueurs restent pseudonymes par défaut. Nom et téléphone seulement avec consentement, masqués pour le staff, purgés automatiquement.
  5. Trois réponses bloquent le démarrage du code : le modèle économique, l'endroit où tourne le jeu aujourd'hui, et l'URL des QR codes déjà imprimés.

Dix décisions structurantes à valider

D1

Trois applications séparées dans un seul dépôt

app.detectivescan.com pour les hôtels, admin. pour ton équipe, go. pour les joueurs. Trois apps Next.js qui partagent le design system, la base et la logique métier (monorepo).

Pourquoi
Tu veux deux environnements totalement distincts. Chaque app se déploie seule, le code admin ne part jamais chez les hôtels, et l'app joueur reste ultra-légère.Sinon
Une seule app découpée en sections : plus rapide la première semaine, plus risquée ensuite.
D2

Multi-tenant : hotel_id partout, verrouillé par la base

Une base partagée. Chaque ligne porte l'hôtel auquel elle appartient, et Postgres (Row Level Security) refuse toute lecture hors de son hôtel. Une table organizations regroupe les hôtels d'un même client.

Pourquoi
Deux verrous au lieu d'un : même un bug applicatif ne peut pas exposer un autre hôtel. Les groupes hôteliers et la facturation se gèrent sans refonte.Sinon
Une base par hôtel : isolation maximale, mais chaque migration à répéter N fois.
D3

Supabase (région UE) + Drizzle ORM

Postgres, authentification (2FA incluse), stockage de fichiers privés et RLS chez un seul fournisseur, hébergé à Paris ou Francfort.

Pourquoi
Couvre 4 besoins du brief avec un seul service, données en UE, open source donc réversible.Sinon
Neon + Better Auth + stockage S3 : plus modulaire, 2 à 3 semaines d'intégration en plus.
D4

Le QR code ne contient jamais le numéro de chambre

URL courte avec identifiant aléatoire (go.detectivescan.com/q/7Kp3xQ), code lisible imprimé dessous (01-254-00), association QR ↔ chambre historisée.

Pourquoi
Déplacer un QR sans le réimprimer, garder des stats justes dans le temps, empêcher qu'on devine les URL pour gonfler les scans.Sinon
URL lisible (/q/01-254-00) : plus simple, mais énumérable.
D5

Joueurs pseudonymes par défaut

Nom et téléphone uniquement si le joueur les donne (ex. pour recevoir un lot), avec consentement explicite, masqués pour le staff, purgés après 90 jours (durée à valider).

Pourquoi
RGPD, confiance des hôtels, et 95 % des statistiques n'ont pas besoin d'identité.Sinon
Collecte systématique : plus de données, plus de risque juridique et de friction au démarrage du jeu.
D6

Campagne = conteneur ; le contenu vit dans des variantes

Toute campagne a au moins une variante A. L'A/B testing consiste à en ajouter une B, avec un poids d'affichage.

Pourquoi
L'A/B testing est prêt côté données dès le MVP, sans refonte. L'interface A/B arrive en V2.Sinon
Contenu dans la campagne : migration de données obligatoire le jour de l'A/B.
D7

CRM, agenda, signature et coffre-fort en V2, par adaptateurs

Le cœur définit des interfaces (CalendarProvider, SignatureProvider…). Ton code open source s'y branche comme un service séparé.

Pourquoi
Ce sont quatre produits à part entière. Au lancement, la valeur se joue côté hôtels. Beaucoup de ces projets sont sous licence AGPL : les garder séparés protège ton code.Sinon
Tout au MVP : 6 à 10 semaines de plus avant le premier hôtel en ligne.
D8

Lancement sur invitation, inscription libre en V2

Ton équipe crée l'hôtel dans l'admin, installe les QR, puis invite l'admin de l'hôtel par e-mail.

Pourquoi
L'installation est physique : un hôtel inscrit seul n'a rien à voir tant que les QR ne sont pas posés.Sinon
Inscription libre dès le MVP : utile seulement avec un kit QR expédiable.
D9

Le jeu se branche par un contrat d'événements signé

partie.commencée, partie.terminée (gagné ou perdu), avis.envoyé, rattachés au scan par un jeton signé.

Pourquoi
Fonctionne que le jeu soit reconstruit dans go. ou conservé là où il tourne aujourd'hui.Dépend de
Ta réponse à la question 5.
D10

Le modèle économique décide de la place de Stripe

Ton offre actuelle dit « sans coût pour l'hôtel », le brief prévoit abonnements et MRR. Proposition : Découverte gratuite (jeu + stats essentielles), Pro payant (campagnes, analytics, export), Groupe (multi-hôtels, A/B).

Pourquoi
Garde la promesse « sans coût » pour signer vite, et monétise ce qui prouve le ROI.Si tout reste gratuit
Stripe passe en V2, l'abonnement devient un simple statut géré par l'admin.

Comment c'est codé

Une permission est une clé (campaigns:publish, players:pii:read…). Un rôle est une liste de clés stockée en base : créer un rôle « Marketing hôtel » ne demande aucune ligne de code.

Chaque action serveur appelle authorize() avant d'agir. La base vérifie une seconde fois avec la Row Level Security : un oubli dans le code ne suffit pas à exposer un autre hôtel.

Le masquage des données personnelles se fait côté serveur : un Hotel Staff ne reçoit jamais le numéro complet dans son navigateur.

// packages/auth/permissions.ts
export const PERMISSIONS = {
  "campaigns:publish": "Activer une campagne",
  "players:pii:read":  "Voir nom et téléphone",
  "qr:assign":         "Associer un QR à une chambre",
} as const;

// apps/hotel/…/campaigns/actions.ts
export async function publishCampaign(hotelId, id) {
  const actor = await requireSession();
  await authorize(actor, "campaigns:publish", { hotelId });
  await campaigns.publish({ hotelId, id, actor });
  // → écrit aussi une ligne dans audit_logs
}

Beaucoup d'air, peu de couleurs, une seule action mise en avant par écran.

Le laiton signale l'action

Chaque page s'ouvre sur le chiffre ou le statut ; le détail vient au clic.

Le jour pour travailler, la nuit pour jouer

Dashboards clairs par défaut, mode sombre au choix ; expérience joueur immersive en thème nuit.

Discret par défaut

Données personnelles masquées, confirmation explicite avant toute action destructrice.

Règles du schéma

  • hotel_id sur chaque table d'hôtel, avec sa politique RLS.
  • UUID v7 (triables dans le temps) ; aucun identifiant séquentiel exposé.
  • La chambre est figée sur chaque scan et chaque partie.
  • Statuts calculés depuis les dates pour les campagnes : pas de tâche planifiée qui peut rater.
  • Montants en centimes, dates en UTC, affichage dans le fuseau de l'hôtel.
  • Suppression logique pour les contenus ; suppression réelle ou anonymisation pour les données personnelles.
  • Index (hotel_id, occurred_at) sur scans, parties, événements ; partitionnement mensuel des scans en V3 si le volume l'exige.

alter table scans enable row level security;

create policy "membres de l'hôtel" on scans
  for select using ( public.is_hotel_member(hotel_id) );

create function public.is_hotel_member(h uuid)
returns boolean language sql stable
security definer set search_path = '' as $$
  select exists (
    select 1 from public.hotel_users
    where hotel_id = h
      and user_id = (select auth.uid())
      and status = 'active'
  );
$$;

Sécurité : cinq verrous successifs

  1. SessionCookie httpOnly et sécurisé, rotation, sessions révocables. 2FA obligatoire pour l'équipe.
  2. GardeChaque requête vérifie que l'utilisateur appartient à l'hôtel de l'URL.
  3. Permissionauthorize() avant chaque action ; données personnelles masquées côté serveur.
  4. BaseLa RLS refuse ce que le code aurait laissé passer.
  5. JournalChaque action sensible est écrite dans audit_logs, en ajout seul.

RGPD

  • Minimisation : IP hachée, jamais stockée en clair ; aucun cookie publicitaire ; identifiant technique anonyme pour compter les visiteurs.
  • Consentement explicite et séparé pour le nom et le téléphone, et pour toute communication marketing.
  • Conservation : données identifiantes purgées ou anonymisées après 90 jours (à valider) ; statistiques agrégées conservées.
  • Droits : export et suppression depuis les paramètres de l'hôtel et le back-office, tracés dans l'audit.
  • Contrats : CGV et accord de sous-traitance (DPA) signés par chaque hôtel ; registre des traitements tenu à jour.
  • Hébergement UE : Vercel Paris, Supabase Paris ou Francfort, Sentry et Resend en région UE.
  • API joueur : chaque entrée validée, débit limité, jetons signés. Impossible de forger une partie gagnée.
  • Secrets côté serveur uniquement ; la clé serveur de la base n'existe que dans l'admin et les tâches planifiées.
